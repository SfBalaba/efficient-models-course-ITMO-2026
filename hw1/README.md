## Протокол

- `eval()` + `torch.inference_mode()`, FP32; `cudnn.benchmark = False`, TF32 выключен (cuDNN и matmul).
- Вход — случайный тензор `B × 3 × S × S`.
- Сетка: S ∈ {32, 64, 128, 224, 256, 384, 512} ∪ {112, 272, 368, 448}; B ∈ {1, 2, 4, …, 256} ∪ {33, 229, 252}.
  Случайные значения выбраны с `seed = 2026`. Точка считается валидационной (`is_validation = 1`),
  если случайно выбраны её S или B: 63 точки train, 69 validation.
- **Latency** — медиана wall-clock одного прохода (`synchronize` до и после), 10 прогревочных + до 100 повторов.
  Рядом записана медиана GPU-времени по CUDA events (`latency_gpu_s`).
- **Memory** — `torch.cuda.max_memory_allocated()` за один проход. Включает веса, входной тензор
- **Energy** — счётчик энергии NVML (`nvmlDeviceGetTotalEnergyConsumption`) на окне ≥ 2 с
  непрерывных проходов, делённый на число проходов.
- Перед сеткой — 3 с прогрева GPU; OOM ловится и записывается как `status = OOM`.

## Обсуждение: почему формулы ошибаются

**Latency — вырожденная регрессия.** При S, кратных 16, размеры всех слоёв пропорциональны S². Поэтому
FLOPs = B·(αS² + c₁) и `memory()` = 4P + B·(βS² + c₂), их корреляция равна 0,9999999975. Разделить вклад compute
и memory регрессия не может: θ_comp < 0, θ_launch < 0, а их компенсирует слагаемое 4P·θ_mem.

В linear небольшие части признаков, не пропорциональные S², умножаются на огромные коэффициенты.
При S=32, B=256 оно добавляет 1,26 мс, отсюда +179 %. Линейная модель не разделит compute и memory по FLOPs и байтам на этой сетке: все признаки пропорциональны B·S². Разделение даёт только профилирование по слоям или θ-константы, зафиксированные по конфигурации GPU.   
Кроме того, в формулу подаётся пиковая аллокация memory(),
а не объём трафика (bytes moved).

Проверка: per-layer roofline

T = max(0,2 мс, Σ F_conv / (0,35 · P) + Σ bytes_elementwise / (0,85 · BW)),

с КПД из трасс и без подгонки к сетке даёт MAPE **18 %** на всей сетке и 12 % при S ≥ 224. У обученных θ — 38 %.

Что не учтено:
- **плато** от ядер с малой загрузкой GPU (см. выше);
- **переключения алгоритмов cuDNN** при `benchmark=False`: S = 256 и 272 при B = 64–229, S = 368 и 384 при B = 32–64,
  S=128 при B = 229–256 дают −17…−41 %; S = 64 и 128 при B = 4 дают скачки памяти на 33–40 MiB. Скачки есть и на базовой сетке,
  то есть они не связаны с тем, что B или S не степень двойки.

**Memory — что не учли в аналитической формуле `memory()`** (сверено с аллокациями в трассах, `profile_memory=True`):    
Аналитическая модель памяти была уточнена на основе профилирования аллокаций. Выявлено, что пиковое потребление определяется не суммой активаций, а максимумом одновременно живых тензоров + временными буферами библиотек ядра (cuDNN workspace до 732 MiB, int64-индексы MaxPool, cuBLAS workspace ~13 MiB). Для предсказания латентности необходимо использовать метрику Data Traffic (read/write), а не Peak Allocated Memory, так как последние включают непропорциональные накладные расходы, искажающие калибровку.
Модель с пунктами 1, 2, 5 ([memory_model.png](results/figures/memory_model.png)) совпадает с замером до 0,1 % в 50 из 132 точек
и ни разу не превышает замер. Остаток — пункты 3–4. У `memory()` отношение к замеру 0,14–2,87:
×2,87 на больших входах (суммирует всё) и ×0,14–0,5 на малых (нет cuBLAS и workspace).

**Energy — принята постоянная мощность.** Формула E = θ₀ + 248 W · T̂ предполагает постоянную мощность на уровне лимита.
Измеренная мощность — от 57 до 261 W, при S ≤ 64 медиана 114 W. Отсюда завышение в 2–5 раз на малых входах,
плюс ошибка из latency перетекает сюда. Там, где GPU упёрт в лимит (S ≥ 448, B ≥ 8), ошибка ≤ 7 %. Физичнее модель
E = P(загрузка) · T с P от idle 45,6 W до лимита 250 W или E = P_idle · T + e_F · FLOPs + e_B · bytes.

**FLOPs совпадают с `FlopCounterMode`, но это проверка арифметики**, а не реально выполненной работы. Оба счётчика
считают только conv и addmm с 1 MAC = 2 FLOP. cuDNN же на малых входах использует Winograd (`winograd_nonfused` в трассе S=32),
где реальных умножений меньше.


Кстати, если бы при замере применили фьюзинг слоёв, то он избавит от  избыточного обращения к памяти и неэффективного использования вычислителя. 

**Гипотезы для ускорения (не измерялись):**
- TF32 / tensor cores для свёрток (основная доля времени);
- `cudnn.benchmark=True` вместо эвристик;
- объединение conv с ReLU;
- MaxPool без int64-индексов в инференсе (минус 2 × выход pool в пике памяти).

**Вердикт.**
1. Коэффициенты theta.json физически неинтерпретируемы: два знака невозможны, θ_mem отличается от паспорта ×1430.
   Это следствие коллинеарности признаков, а не свойства железа.
2. Паспортный roofline даёт нижнюю границу времени: реальное время в 2,1–3,2 раза больше при насыщении.

   - память — ×1,15 от паспорта;

4. Для предсказания нужна формула по слоям с КПД. Без подгонки к сетке она даёт MAPE 18 % против 38 % у theta.json.

## Выводы

Стандартная формула «сумма всех активаций» дала ошибку ×2.87 из-за игнорирования внутренней логики GPU-библиотек. Корректная модель пикового потребления должна включать:    
 -  живых тензоров - это не сумма, а максимум одновременно живых тензоров (max(In_mem + Out_mem)`), так как фреймворк переиспользует буферы для последовательных слоев.   
- Временные буферы, которые не видны в графе вычислений (*cuDNN Workspace)
-  MaxPool Indices: Для обратного прохода требуется int64-тензор размером 2 * Output_{pool}$, что создает пиковый всплеск, скрыто в логике ядра.    

**Вывод**: для определения latency — модель трафика (количество прочитанных и записанных байт). Подстановка Peak Memory в формулу для вычисления Latency приводит к вырожденной регрессии из-за мультиколлинеарности с FLOPs s^2    

Предположение о постоянной мощности E = TDP * T верно только в Compute-bound режиме .
На малых входах gpu работает в memory/launch-bound режиме, потребляя меньше, чем пиковое потребление 250 Вт. Использование TDP завышает оценку энергии в 2–5 раз.
**Коррекция:** $E = P_{base} \cdot T + e_{comp} \cdot FLOPs + e_{mem} \cdot Bytes$, где $P_{base}$ — статическое потребление idle-состояния (~45 Вт).

Roofline и режимы работы:    
Для данной конфигурации (FP32: 41.9 TFLOPS, HBM: 896 GB/s) Ridge Point составляет **~46.8 FLOP/Byte**.
 - Свертки:** ArI > 1000 → строго Compute-bound. latency ограничена пиковыми TFLOPS.
 - Поэлементные операции (ReLU, Pool, GAP):** ArI << 46.8 → Memory-bound. Их вклад в общую ошибку аналитической модели латентности критичен, так как они не масштабируются линейно с FLOPs.
 - Мультиколлинеарность: На сетке параметров, где $S$ кратно 16, все признаки пропорциональны $B \cdot S^2$. Разделить $\theta_{comp}$ и $\theta_{mem}$ регрессией невозможно без изменения экспериментальной сетки или фиксации $\theta$ по конфигурации. 

Оптимизации и архитектура:   
-  Fusion: Объединение слоев (Conv+BN+ReLU) устраняет избыточный трафик и launch-overhead, что критично для memory-bound операций.
 -  Batch Size: Для малых $S$ увеличение батча дает кратный выигрыш в throughput и энергии на изображение, amortizing launch overhead.
 - *Типы данных: Для тензорных операций (свертки, MatMul) предпочтителен TF32/FP16. Скалярные FP32 операции не используют Tensor Cores эффективно и остаются в CUDA-ядрах, снижая общую утилизацию. *(Примечание: TF32 доступен только для матричных умножений и сверток; для поэлементных операций он не применяется).*

### 5. Итог по аналитической оценке
Аналитическая формула верна для FLOPs (MAE=0), но требует компонентного подхода для Latency и Energy:
1. latency - считать отдельно для Compute-bound (Conv/Linear) и Memory-bound (Element-wise) слоев. Использовать Traffic, а не Peak Memory.
2. memory - yчитывать Live Tensors + Library Workspaces.
3. energy -использовать динамическую мощность, зависящую от режима (Compute vs Memory bound).
4. Параметры $\theta$ можно фиксировать по спецификации GPU (41.9 TFLOPS / 896 GB/s).
